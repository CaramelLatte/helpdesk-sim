# AI Help Desk Simulation Trainer

A self-hosted training environment that simulates the full lifecycle of an IT help desk ticket. A stateful AI persona files and responds to tickets like a real (variably patient, variably technical) end user. The operator works the ticket — including running diagnostic commands against a simulated shell — and a separate grading model evaluates performance afterward.

Built as a portfolio and personal learning tool to demonstrate skills that entry-level help desk and SOC postings screen for but rarely test directly: ticket communication quality, correct diagnostic sequencing, and knowing when to escalate rather than always attempting a direct fix.

---

## How it works

When a ticket is created, the system:
1. Randomly rolls a **persona** — a set of numeric traits (patience, technical literacy, verbosity, formality, mood volatility) that shape how the simulated user writes and responds
2. Selects a **scenario** (a YAML file describing the problem, available diagnostic commands, and resolution paths)
3. Uses a small, fast local LLM to generate the opening ticket message in that persona's voice
4. Creates the ticket in Zammad

The operator works the ticket through two interfaces:
- **Zammad web UI** — for reading and responding to the user (the persona replies automatically when the operator writes back)
- **Shell client** — a fake terminal that accepts diagnostic commands and returns deterministic, scenario-appropriate output

When finished, the operator takes their resolution action in Zammad (close or reassign/escalate), then runs the shell client's `close` command. The system reads the actual Zammad ticket state, computes timing metrics, and passes the full session to a larger grading model for evaluation.

---

## Prerequisites

- **Python 3.10+**
- **Zammad** (self-hosted) — tested against Zammad 6.x
  - Default assumes `localhost:8080`. Any host/port works via `.env`.
- **LM Studio** — or any OpenAI-compatible local inference server
  - Two models are used: a smaller/faster one for the persona, a larger one for grading
  - Tested with models in the 7B–120B range

## Zammad one-time setup

These steps only need to be done once. They survive ticket cleanup.

1. **Install and start Zammad.** The Docker Compose method is easiest: https://docs.zammad.org/en/latest/install/docker-compose.html

2. **Create an API user account** (`Admin > Users > New User`):
   - Email: something like `ai.user@yourinstance.local`
   - Role: **Admin**
   - This account acts as the system's identity in Zammad

3. **Generate an API token** for that account:
   - Log in as the API user
   - `Avatar > Profile > Token Access > Create`
   - Copy the token — it only displays once

4. **Create an escalation group** (optional but recommended):
   - `Admin > Groups > New Group` — name it something like `Network Team` or `Dev Team`
   - This is the group you'll reassign tickets to when escalating in a scenario that requires it

## Installation

```bash
git clone <repo-url>
cd ai-ticket
pip install -r requirements.txt
cp .env.example .env   # then edit .env with your values
```

If there's no `.env.example`, copy the block below into a new `.env` file:

```env
API_KEY=your_zammad_api_token_here
USERNAME=ai.user@yourinstance.local
PASSWORD=your_zammad_user_password

FLASK_HOST=127.0.0.1
FLASK_PORT=5001

ZAMMAD_HOST_ADDRESS=localhost
ZAMMAD_PORT=8080

LM_STUDIO_ADDRESS=localhost
LM_STUDIO_PORT=1234
TICKET_GEN_MODEL=your-persona-model-name
GRADING_MODEL=your-grading-model-name

SCHEDULER_INTERVAL_SECONDS=60
CLEANUP_AFTER_HOURS=24
```

`TICKET_GEN_MODEL` and `GRADING_MODEL` should match the model names exactly as they appear in LM Studio.

## Running the server

```bash
python app.py
```

On startup the server:
- Initializes the SQLite database (`ai_ticket.db`) if it doesn't exist
- Connects to Zammad and fetches the API user's ID
- Starts the background scheduler (persona polling + automatic ticket cleanup)

## Operator workflow

### 1. Create a ticket

```bash
curl -s -X POST http://localhost:5001/api/tickets \
  -H "Content-Type: application/json" \
  -d '{"scenario_id": "dns_failure"}' | python -m json.tool
```

Available scenario IDs:
```bash
curl -s http://localhost:5001/api/scenarios | python -m json.tool
```

The response includes a `zammad_url` — open it in your browser to see the ticket.

### 2. Work the ticket

Open two windows:

**Window 1 — Zammad browser UI**
Use the URL from the create response. This is where you communicate with the simulated user. The persona will reply automatically when you comment on the ticket (replies are generated by the LLM based on the persona's traits and current mood).

**Window 2 — Diagnostic shell**
```bash
python shell_client.py --ticket <ticket_id>
```
Type diagnostic commands as you would in a real terminal. Type `log` to see what you've run so far.

### 3. Resolve the ticket

Take your resolution action **in Zammad first**:
- **Direct fix**: mark the ticket **Closed** in the Zammad UI
- **Escalation**: reassign the ticket to the appropriate group in Zammad (leave it open)

Then, in the shell client, type:
```
close
```

You'll be prompted for brief resolution notes. The grading model runs and your performance review prints to the terminal.

## Grading dimensions

| Dimension | What it measures |
|---|---|
| Diagnostic accuracy | Did you correctly identify the root cause (or recognize it exceeded T1 scope)? |
| Diagnostic efficiency | Was your command sequence logical given what was available? |
| Escalation judgment | Did you escalate correctly, to the right tier, with appropriate groundwork? |
| Response timeliness | Time to first response; how many times the persona had to follow up |
| Customer service | Professionalism, clarity, empathy, plain language vs. jargon, closing the loop |

**Correct escalation is a full-credit resolution**, not a fallback. Scenarios that require escalation are scored such that diagnosing-and-escalating is the top path.

## Available scenarios

| ID | Title | System | Correct resolution |
|---|---|---|---|
| `dns_failure` | DNS Resolution Failure | Linux desktop | Fix (nmcli) + verify, or escalate with diagnosis |
| `service_down` | Web Application Service Down | Linux server | Escalate to dev team with log evidence |
| `account_lockout` | User Account Locked Out | Linux server | Direct fix (faillock reset) + verify |
| `disk_full` | Disk Full — Application Write Errors | Linux server | Escalate to sysadmin with evidence |
| `printer_offline` | Printer Offline — Stuck Print Queue | Windows desktop | Direct fix (clear stuck job) + verify |
| `expired_password` | Remote User Locked Out — Expired Password | Windows / AD | Direct fix (unlock **and** reset) + verify |
| `mapped_drive` | Mapped Network Drive Unavailable | Windows desktop | Direct fix (delete + remap) + verify |
| `wrong_wifi` | Mac on Wrong Wi-Fi — Internal Resources Unreachable | macOS laptop | Direct fix (rejoin corp SSID) + verify |

Direct-fix scenarios distinguish a **verified** fix (re-running the diagnostic afterward to confirm) from an unverified one — verifying scores highest. Several scenarios also contain deliberate traps: restarting the spooler without checking the queue, unlocking an AD account without addressing the expired password behind the lockout, or setting a public DNS resolver that can't serve internal names.

## Adding scenarios

Scenarios are YAML files in the `scenarios/` directory. Copy an existing one as a template. Key fields:

- `description` — plain-English summary of the root cause (shown to the grading model)
- `shell` — which OS shell the scenario simulates: `bash` (default), `zsh`, `cmd`, or `powershell`. Controls the "command not found" message and the shell client's prompt.
- `available_commands` — list of commands the operator can use (grader won't penalize for not running anything outside this list)
- `commands` — each command has a `match_pattern` (Python regex), `output` template, and optional `reveals` ID
- `resolution_paths` — each path has `required_discoveries` (set of reveal IDs that must be present) and a `score_modifier` (1.0 = ideal)
- `optimal_path` — ordered list of command IDs representing the most efficient diagnostic sequence

**Important:** if two commands share a prefix (e.g., `faillock --user X` and `faillock --user X --reset`), put the more specific one first — the matcher returns on the first regex match.

Output templates support `{variable}` placeholders filled from `system_state` values and `{target}` (the first argument after the command verb).

### Stateful outputs (`conditional_outputs`)

A command can show different output once certain discoveries exist — this is how fix-action commands change what the shell reports afterward. Each entry has `requires` (one discovery ID or a list, all of which must be present), its own `output`, and optionally its own `reveals`. Entries are checked in order; the first satisfied one wins, otherwise the base output is used.

```yaml
- id: faillock_check
  match_pattern: "^faillock\\s+--user\\s+\\S+"
  output: |
    (...lockout entries...)
  reveals: "account_locked_by_faillock"
  conditional_outputs:
    - requires: lockout_reset
      output: |
        (...empty tally...)
      reveals: "reset_verified"
```

This enables the verify-your-fix pattern: gate a `fix_verified` discovery behind re-running a diagnostic after the fix, then require it in the top-scoring resolution path. It also supports realistic ordering constraints (e.g. `net use Z:` fails with "device name already in use" until the stale mapping has been deleted).

**YAML gotcha:** if the first line of an `output` block starts with spaces (e.g. `free -h` or `dir` output), use an explicit indentation indicator (`output: |2`) or the file won't parse.

## Ticket cleanup

Graded tickets older than `CLEANUP_AFTER_HOURS` are automatically deleted from both Zammad and the local database. The cleanup job runs every 6 hours.

To trigger cleanup manually (useful before a demo):
```bash
curl -s -X POST http://localhost:5001/api/admin/cleanup
```

To disable auto-cleanup, set `CLEANUP_AFTER_HOURS=0` in `.env`.

Open (in-progress) tickets are never auto-deleted.

## Architecture overview

```
app.py                  Flask entry point; starts scheduler on boot
config.py               All settings loaded from .env
db.py                   SQLite schema and helpers
routes/
  tickets.py            Ticket lifecycle endpoints (create, get, close, cleanup)
  shell.py              Shell simulation endpoints (run command, get log)
services/
  zammad.py             Zammad REST API wrapper
  llm.py                LM Studio client (OpenAI-compatible)
  persona.py            Trait rolling, mood state machine, system prompt builder
  scenario.py           YAML loader, command matcher, resolution path evaluator
  scheduler.py          APScheduler: persona polling, proactive follow-ups, cleanup
scenarios/
  *.yaml                One file per scenario — the core authoring asset
shell_client.py         Standalone CLI for the diagnostic shell
```

The two-model split is intentional: the persona model runs at every scheduler tick and needs to be fast; the grading model runs once at ticket close and can take more time in exchange for better reasoning.

## Public UI integration

The API is designed to support a browser-based UI that replaces both the Zammad web interface and the shell client with a unified experience. In that configuration, Zammad operates as a backend engine — ticket storage and message threading only — and the operator never opens a Zammad tab.

### Endpoints added for UI support

**`GET /api/tickets/<id>/thread`**
Returns the public conversation thread, ready for display. Internal notes (shell logs) are excluded. Each message includes `role` (`user` or `operator`), `body`, `timestamp`, and `article_id`. Poll this every 5–10 seconds while a ticket is open — persona replies appear here as the scheduler generates them.

**`POST /api/tickets/<id>/reply`**
Posts an operator message to the ticket thread. Body: `{"message": "..."}`. The persona scheduler detects the new message and generates a reply automatically. Returns the posted article's ID and timestamp.

**`PATCH /api/tickets/<id>/state`**
Sets the Zammad ticket state and/or group without triggering grading. Call this when the operator commits to a resolution, before calling `/close`.

| Scenario | Body |
|---|---|
| Operator resolved it directly | `{"state": "closed"}` |
| Operator escalating to a group | `{"group": "Network Team"}` |
| Both at once | `{"state": "open", "group": "Dev Team"}` |

### UI session flow

```
GET  /api/scenarios                    populate scenario picker
POST /api/tickets                      start session, store ticket_id

GET  /api/tickets/<id>/thread          render conversation pane (poll every 5–10s)
POST /api/tickets/<id>/reply           operator sends a message
POST /api/shell/<id>/command           operator runs a diagnostic command
GET  /api/shell/<id>/log               update command history panel

PATCH /api/tickets/<id>/state          operator commits resolution (close or escalate)
POST  /api/tickets/<id>/close          submit notes, receive grading rubric
```

The persona, LLM calls, and scheduler are entirely backend — the UI never interacts with them directly.
